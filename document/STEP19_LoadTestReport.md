### 1. 개요

**핵심 API 4종**에 대해 k6 기반 부하 테스트를 수행하고, 성능(SLO) 충족 여부와 시스템 안정성을 검증했다.

대상 기능:

* 포인트 충전 (PATCH `/point/charge/{id}`)
* 선착순 쿠폰 발급 (POST `/api/new/coupons/{couponId}/issue`)
* 인기상품 랭킹 조회 (GET `/products/rank/today`)
* 주문/결제 (POST `/orders`)

### 2. 테스트 대상 선정 및 목적

| 시나리오       | 목적                                  | 위험요소                                    | SLO                              |
| ---------- | ----------------------------------- | --------------------------------------- | -------------------------------- |
| **포인트 충전** | DB Connection Pool 안정성 및 트랜잭션 지연 검증 | Hikari Pool 고갈, 락 경합                    | p95 < 250ms, p99 < 600ms         |
| **쿠폰 발급**  | 재고 소진 및 중복 방지 로직 검증                 | 분산락 병목, 409 과다 발생, 재시도 폭주               | p95 < 250ms, p99 < 600ms, 409 허용 |
| **랭킹 조회**  | Redis 캐싱 성능, 읽기 API 대량 호출 검증        | 캐시 TTL 만료 시 트래픽 집중, Redis connection 고갈 | p95 < 200ms, p99 < 400ms         |
| **주문/결제**  | 재고/쿠폰/포인트 통합 경합 및 E2E 지연 검증         | DB/Redis/Kafka 다중 자원 경합, 분산락 타임아웃       | p95 < 300ms, p99 < 800ms         |

### 3. 시나리오 및 워크로드 모델

k6 **ramping-arrival-rate**로 초당 요청 도착률(ARR)을 제어하며 단계별로 부하를 증가시켰다.

| 시나리오  | 단계                                              | 지속  | 목표 ARR                    | 비고         |
| ----- | ----------------------------------------------- | --- | ------------------------- | ---------- |
| 포인트충전 | Warm-up → Steady → Ramp → Spike → Cool-down     | 33m | 20 → 20 → 60 → 120 → 0    | maxVUs 200 |
| 쿠폰발급  | Warm-up → Steady → Spike → Recovery → Cool-down | 28m | 50 → 50 → 150 → 50 → 0    | maxVUs 300 |
| 랭킹조회  | Warm-up → Steady → Ramp → Spike → Cool-down     | 38m | 200 → 200 → 300 → 500 → 0 | maxVUs 300 |
| 주문/결제 | Warm-up → Steady → Ramp → Spike → Cool-down     | 20m | 50 → 50 → 150 → 300 → 0   | maxVUs 400 |

| **상태코드 분포** | 100% 200             | <400 or 409 OK      | 100% 200            |

**추가 관측:**

* 평균 응답시간: ranking 1.58ms, coupon 5.42ms, charge 18.35ms → 읽기 API는 거의 실시간 수준.
* VU peak: 210, 안정적.
* metric tag >100k 경고 → userId 등 high-cardinality 태그는 후속 실행 시 groupBy 적용 권장.

#### ⚠️ 주문/결제 (문제 발견)

| 지표         | 측정값          | SLO    |
| ---------- | ------------ | ------ |
| **p95**    | **59.99s** ✗ | <300ms |
| **p99**    | 60s ✗        | <800ms |
| **에러율**    | **7.9%** ✗   | <1%    |
| **2xx 비율** | 92.1%        | -      |
| **5xx 비율** | 7.9%         | -      |

**추가 관측:**

* 평균 응답시간 4.65s (비정상적으로 높음), max=60s.
* dropped\_iterations 71k → VU가 도착률을 감당 못함.
* 705건 5xx 발생 → 동시성 제어/락 타임아웃 원인 분석 필요.
* iteration\_duration p95=60s → 큐잉 또는 락 경합 심각.

**결론:**

* 포인트/쿠폰/랭킹은 SLO 충족 → 안정적.
* 주문/결제는 **성능 목표 미달 (p95 59.99s, 에러율 7.9%)** → 원인 분석 및 튜닝 필요.

    * DB/Redis 락 대기시간, Kafka Outbox 처리 병목, 트랜잭션 경합 구간 점검.
    * 대기시간(lease/waitMs) 재조정, 재시도 로직, 스레드 풀 크기 검토.
    * 재테스트 필요.
